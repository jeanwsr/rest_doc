- **日期**：2026-09-16

- **作者**：GLM-5.3 (经祝震予 (ajz34@outlook.com) 的 mattpocock-skills:grill-with-docs 会话起草)

## 决定

- REST 以 ADR 记录重要的技术决定：影响多个模块、或日后难以更改的决定，记录其背景、选择与理由。
- 每个 ADR 只记录一个决定，文件名 `adr-NNNN-slug.md`，编号自 ADR-0001 起递增；本篇是使用规范与说明本身，不是编号 ADR。
- ADR 是历史记录而非活文档：一经生效不再改写实质内容；决定变更时撰写新的 ADR 接替，旧 ADR 仅作非实质更新——更新状态，或以 取代/部分取代 字段与受影响章节处的提示标注被接替的部分 (见 3.1 节)，不改动其余内容。
- ADR 状态取值：`提议中` / `已否决` / `使用中` / `存在争议` / `已取代 (ADR-NNNN)` / `已废止`。`提议中` 经维护者确认后置为 `使用中`；`存在争议` 期间决定仍然有效，直至争议解决并另作处置。
- ADR 的决定部分对适用范围内的后续代码具有约束力；存量代码允许存在未遵循之处，在适用范围字段中以一句话说明即可，不维护文件级清单。
- 本篇是活文档：规则可由维护者直接修订并更新日期，无需以新 ADR 接替。通过 git blame 可追踪历史修改记录。
- 撰写或评审 ADR 由人类开发者主导，建议借助 code agent 的 `grill-with-docs` 等 skill 进行 (见第 4 节)。

## 1. 什么是 ADR

ADR (Architecture Decision Record, 架构设计决定) 是软件工程中的一项轻量实践：用一篇短文档记录一个技术决定——当时面对什么问题、有哪些现实可选的方案、选了哪一个、为什么。

"架构"一词并不意味着只有宏大的系统设计才配写 ADR。只要会长期约束后续代码，都属于架构决定；这包括代码规范、工程技巧、测试流程等等。

ADR 最重要的价值在于记录 **为什么**。代码本身和 API 文档能告诉读者程序"是什么"、"怎么用"，但回答不了"为什么不用另一种看起来更自然的做法"。这些理由在讨论发生时人人都知道，一年之后却只剩猜测。ADR 把判断的依据连同被否决的方案一起留在纸面上，未来的读者 (也包括 AI agent) 才能判断当年的前提今天是否仍然成立。

## 2. 何时写 ADR：与其他文档的区别

| 文档种类 | 回答的问题 | 生命周期 | 实例 |
| --- | --- | --- | --- |
| ADR | 为什么作这个决定 | 决定时写定，作为历史保留 | 本目录各文档 |
| API 文档 | 这个接口/参数怎么用 | 随接口持续更新 | rustdoc |
| 开发者文档 | 代码如何组织、如何参与开发 | 持续维护 | 编译指南、模块说明 |
| 增强提案 | 我们将来要做什么 | 提案—评审—实施，实施后归档 | Python PEP、NumPy NEP、Rust RFC |

关键区别在生命周期。API 文档与开发者文档描述 **现状**，要随代码持续更新；增强提案面向 **未来**，用于在动手之前就新功能达成共识；ADR 是 **快照**，记录决定作出那一刻的判断，不随代码演化而改写。同一次工作往往同时涉及几类文档：新功能可以先写增强提案讨论，实施后其用法进入 API/用户文档；而技术选型无论发生在编写代码前，还是实施中沉淀为长期有效的约定，都写成 ADR。

REST 目前没有正式的提案流程与生命周期维护：方向性共识多在组内当面讨论或 Gitee issue/PR 中达成，也常直接以实现落地。因此上述流程是业界通行做法，而非 REST 的现状。

满足下述任一情形时，应考虑写 ADR：

- 决定的约束超出了、或将要超出单个模块或单次 PR；
- 决定作出后难以反转，或反转代价高昂；
- 决定是在多个现实可行的方案中取舍的结果，可以预见未来有人会问"为什么不那样做"。

反之，局部实现细节、bug 修复、不引入新决定的重构，不需要 ADR，代码注释或 PR 描述足以承载。

## 3. 如何撰写 ADR

### 3.1 结构

ADR 位于 `rest_doc/source_zh/contributor/adr/`，文件名 `adr-NNNN-slug.md`，并登记在本目录 `index.md` 的 toctree 中。结构如下：

- 头部元信息，各一行：
  - **状态**：`提议中` / `已否决` / `使用中` / `存在争议` / `已取代 (ADR-NNNN)` / `已废止`；
  - **日期**：决定实际生效的日期。若决定伴随代码机制落地，取机制落地的日期 (可由 git 历史考证)，而非文档撰写之日；
  - **适用范围**：决定约束哪些 crate/模块；存量代码尚未遵循之处，在此以一句话说明；
  - **作者**：起草者，可以是人类开发者或 AI agent；
  - **审阅** (可选)：agent 起草时，填写负责确认的人类开发者。
  - **取代** (可选)：本篇接替的旧 ADR，可为整篇或具体章节 (如 `ADR-0001 第 3.3 节`)；
  - **部分取代** (可选)：使用中的 ADR 若仅个别部分被新 ADR 接替，在此列出被接替的章节与接替者；受影响章节标题下可附一行日期化提示指向接替者，正文原内容保留不动。
- **决定**：规范性内容。以条目块把规范性内容压缩为几条一眼可读的要点，必要时可附一段最小代码示例；多数读者多数时候只读这一部分，因此它应当脱离正文也能独立成立。
- **正文**：叙述性章节——设计动机、用法、技术细节、备选方案、备注等；正文默认为阐释性内容 (非规范)，个别章节可另行标注 (如"非规范性")。正文是 ADR 有别于干巴巴的规则清单之处：把理由写透，读者才能自行判断前提是否变化。

状态层面的 `已废止` 指整篇决定废止且无接替者，与正文中对单个被否决方案的标注 (见 3.2 节) 是两回事。

### 3.2 写作约定

- 被否决或已废止的方案 **保留在文中**，以"已废止"等字样明确标注，不删除；它们是"为什么不"的最好证据。
- 不维护文件级的符合性清单 (哪些文件遵循、哪些未遵循)。这类清单随代码演化会迅速失效；一句"存量代码存在尚未遵循之处，将在重构中逐步对齐"即可。
- 指向代码或外部资料时给出稳定的位置 (模块路径、源码链接)，避免"当前 PR"之类随时间失效的提法。
- 对于简体中文的编写或翻译，代码、函数名、专有名词保留原文不作翻译。

## 4. AI 时代的工作流

REST 开发者大多并非专业软件工程师；在不具备独立构建 ADR 的能力前，建议借助 code agent 的 `grill-with-docs` skill (来自 [mattpocock/skills](https://github.com/mattpocock/skills)) 或类似工具进行。工作模式建议采取下述两种：

- **开发者主导 prompt，AI 主导生成 ADR**：开发者与 agent 逐轮问答。agent 通读相关代码、核对事实、就设计的每个分支提出尖锐的问题；决定权始终在开发者手中。设计澄清后由 agent 起草 ADR，开发者修改定稿。
- **开发者完成 ADR，AI 评审**：对开发者实现的 ADR，agent 需要作事实分析与结构调整。事实分析需要 agent 逐条核对其论断与当前代码是否一致，指出过时、含混或缺少理由之处。结构调整需要 agent 重新组织内容，使其更符合 ADR 的规范、可读性、以及更契合 AI agent 协作的能力。

强调人类开发者主导：
- ADR 文档的约束性较强。错误的 ADR 相比于没有 ADR 更容易导致代码漂移。
- AI agent 能快速产出通顺的文字，但其中未经核实的论断读起来同样通顺；逐轮问答的流程迫使每条写进 ADR 的论断都经过事实核查与开发者确认。

ADR 也是写给 AI agent 的文档：agent 在生成或修改代码前阅读 ADR，即可遵循其中的规范与禁忌，而不必重新踩一遍前人踩过的坑。

**不建议在一个 AI agent session 内同时完成 ADR 的撰写与代码实现**。AI agent 的输出经常强烈地受 prompt 影响。若在同一 session 内同时进行，容易导致 agent 在撰写 ADR 时就已经被 prompt 引导去考虑代码实现的细节，从而偏离了 ADR 的本意。
